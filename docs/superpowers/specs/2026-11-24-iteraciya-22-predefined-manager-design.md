# Итерация 22: предопределённые элементы как свойства менеджера (дизайн)

Дата: 2026-11-24. Основание: дефект **F83** (итерация 21): конфигурационные члены менеджеров —
17 пар / 89 находок / 30 формных — остались находками после шаблонного наследования.

## 1. Что показала разведка

Артефакт замера 90: 73 находки (30 формных) с владельцем `СправочникМенеджер.<Объект>`,
`ПланВидовХарактеристикМенеджер.<Объект>` и т. п. и членом, которого нет в шаблоне. Проверка по
`<Объект>/Ext/Predefined.xml` корпуса: **все 73 — верхнеуровневые предопределённые элементы**:

- `СправочникМенеджер.ГруппыВнешнихПользователей.ВсеВнешниеПользователи` — 30;
- `СправочникМенеджер.ГруппыПользователей.ВсеПользователи` — 28;
- `СправочникМенеджер.ПапкиФайлов.Шаблоны` — 7;
- `ПланВидовХарактеристикМенеджер.ОбъектыАдресацииЗадач.ВсеОбъектыАдресации` — 4;
- прочие (`СистемнаяУчетнаяЗаписьЭлектроннойПочты`, `ОтветственныйЗаКонтрольИсполнения`,
  `ТекущийПлан`) — по 1–2.

Загрузчик уже разбирает эти файлы: `load/reader.py:1174` пишет
`model["predefined_data"]["<вид>.<имя>"]` = `{"items": [...]}` с полями `name`, `parent`,
`is_folder`. `build_type_model` (`metadata/loader.py:146-180`) регистрирует тип менеджера только
с методами менеджер-модуля и **не переносит** предопределённые имена в свойства. То есть знание
загружено, но не связано с типом.

## 2. Цели

1. В `build_type_model` при регистрации типа менеджера добавлять **верхнеуровневые** имена
   предопределённых данных (`parent == ""`) в `properties`; значение — ссылочный тип объекта
   (`ref_type`), чтобы обращение к предопределённому элементу давало ссылку и её методы.
2. Снять замер **91**: закрыть до **73 находок / 30 формных**, не открыть ни одной новой; лестница
   не выше 2 784 / 616.
3. Не трогать шаблоны, генератор и данные книги: это знание конфигурации, а не платформы.

## 3. Нецели

- Не добавлять вложенные предопределённые элементы на менеджер (они доступны через родителя).
- Не строить канал межмодульных экспортов (M209/соседние шаблоны — отдельно).
- Не менять `semantic.py`, каналы, решения `resolve_member`, фикстуры.
- Не добавлять предопределённые имена в глобальный контекст; только свойства менеджера.

## 5. Подходы

**A. Предопределённые имена в свойствах менеджера (выбран).** Данные уже загружены; связь —
одна строка в `build_type_model`. Закрывает 73 находки, не требует нового канала. Риск — значение
`ref_type` может открыть новые обращения к членам ссылки; гейт 0 открытых; при появлении — значение
`None` (решение в отчёте).

**B. Канал межмодульных экспортов.** Нужен для M209/менеджерских функций, но это отдельный канал с
замером; отклонён для F83.

**C. Ручной список имён.** Нарушает правило данных конфигурации и не переносится на другие
конфигурации; отклонён.

## 6. Механизм

1. В `build_type_model`, после `obj`/`kind`/`ref_type`: взять
   `pre = model.get("predefined_data", {})`; найти запись по `f"{kind}.{obj_name}"`, иначе по
   `f"{spec.get('kind')}.{obj_name}"`, иначе по любому ключу, оканчивающемуся `.{obj_name}`.
2. `props = {norm(item["name"]): ref_type for item in pre.get("items", []) if not item.get("parent")}`.
3. Передать `properties=props` в `TypeDef(name=manager_type, ...)` рядом с `methods=mm`.
4. Ничего больше не менять: имя типа, методы, `kind`, `ctor_arities` прежние. Если `ref_type`
   пуст (вид без ссылок), значение `None`.
5. Что не меняется: модель платформы, шаблоны, каналы, объяснения, фикстуры.

## 9. Риски

1. **Новые находки от `ref_type`**: если ссылка вводит новые обращения — гейт 0 открытых; тогда
   значение предопределённого свойства `None` (решение в отчёте, цена — ссылка не типизируется).
2. **Ключ вида** (`Catalog`/`catalog`/`object`) может не совпасть: искать по трём вариантам и по
   суффиксу `.{obj_name}`.
3. **Вложенные элементы**: на менеджер не попадают (по платформе).
4. **Другие конфигурации**: механизм не зависит от корпуса, работает от загруженной модели.
