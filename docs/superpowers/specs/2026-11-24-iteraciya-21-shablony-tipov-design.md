# Итерация 21: наследование шаблонов типов у квалифицированных имён (дизайн)

Дата: 2026-11-24. Основание: дефект **F82** (итерация 20): составные владельцы — 174 пары / 461
находка / 90 формных. Причина найдена: модель уже держит шаблоны платформенных типов
(`СправочникМенеджер.<Имя справочника>`, `РегистрСведенийНаборЗаписей.<Имя регистра сведений>`,
`ДокументМенеджер.<Имя документа>` и т. п.) с методами и свойствами, но проверка строит конкретное
имя (`СправочникМенеджер.ГруппыПользователей`) и не наследует члены шаблона.

## 1. Что показала разведка

Артефакт замера 89: модельное семейство — 294 пары / 762 находки. Составные владельцы с
префиксами `СправочникМенеджер.`, `РегистрСведенийНаборЗаписей.`, `РегистрСведенийЗапись.`,
`ОбъектМетаданных` — **120 пар / 374 находки**. Сверка с `TYPE_SIGNATURES` (шаблоны с `<…>`):

- **90 пар / 264 находки / 32 формных** — член есть в шаблоне (`РегистрСведенийНаборЗаписей.X.Отбор`,
  `.ДополнительныеСвойства`, `СправочникМенеджер.X.НайтиПоКоду`, …). Наследование закрывает их;
- **30 пар / 110 находок / 43 формных** — члена в шаблоне нет: `СправочникМенеджер.ГруппыПользователей.ВсеПользователи`,
  `.ВсеВнешниеПользователи`, `СправочникМенеджер.ПапкиФайлов.Шаблоны` и подобные. Это члены
  менеджерских модулей конкретной конфигурации (экспорт), не платформенный шаблон.

Шаблоны в модели уже заполнены: `РегистрСведенийНаборЗаписей.<Имя регистра сведений>` держит
`Отбор`, `ДополнительныеСвойства`, `Записывать`, `ОбменДанными`, методы `Вставить`, `Выбран`,
`Добавить`; `СправочникМенеджер.<Имя справочника>` — `НайтиПоКоду`, `НайтиПоНаименованию`,
`Выбрать`, `ВыбратьПоСсылкам` и др. То есть знание есть — не хватает связи «конкретное имя →
шаблон».

## 2. Цели

1. Научить разрешение типа (`TypeModel.resolve_type` / `_resolve_type`) при точном промахе искать
   **шаблон** по самому длинному литеральному префиксу: `Base.<…>` или `Base: <…>`; возвращать
   описание с методами и свойствами шаблона, но **именем конкретного типа** (текст находки не
   меняется) и прежними `kind`/`dynamic_members`.
2. Снять замер **90**: закрыть до **264 находок / 32 формных** (потолок), не открыть ни одной новой;
   лестница не выше 3 306 / 665, ожидаемо 3 042 / ≥ 633.
3. Назвать остаток **110 находок / 43 формных** (конфигурационные члены менеджеров) и записать его
   следующей строкой/дефектом; это не платформенный шаблон.

## 3. Нецели

- Не добавлять в модель члены конкретной конфигурации; не сканировать менеджерские модули.
- Не включать `dynamic_members` и не трогать три канала (ТЗ, поля запроса, форма).
- Не менять решения `resolve_member`: наследование только пополняет `methods`/`properties` типа,
  который иначе оставался без членов.
- Не менять сгенерированные данные и генератор: шаблоны уже есть.

## 4. Ограничения

Наследуются ограничения 1–26 плана итерации 18 и 1–6 итераций 19–20. База — замер 89

## 5. Подходы

**A. Наследование шаблона при разрешении имени (выбран).** Модель уже содержит шаблоны; связь
«конкретное имя → шаблон» — одна ветвь в разрешении типа, без новых данных. Закрывает 264 находки,
не трогает решения и каналы. Риск — неверный шаблон при составном префиксе; снимается выбором
самого длинного литерального префикса и тестами.

**B. Сканировать менеджерские модули конфигурации.** Закрыл бы и `ВсеПользователи`, но это новый
канал межмодульных экспортов с собственным замером и риском ложных закрытий. Отклонён в пользу A;
B — следующая итерация.

**C. Дописать члены в модель вручную.** Нарушает правило сгенерированных данных и не чинит следующие
конфигурации. Отклонён.

## 6. Механизм

1. В `TypeModel.resolve_type` (model.py) после точного промаха: если имя содержит `.` или `: `,
   найти среди зарегистрированных типов шаблон, чей литеральный префикс (до первого `<`) — самый
   длинный и является префиксом имени (`Base.` / `Base: `). Кэшировать результат по конкретному
   имени.
2. Вернуть `TypeDef` с `name` = конкретное имя, `kind` и `dynamic_members` шаблона, `methods` и
   `properties` шаблона (копии; типы значений сохраняются). Никаких новых глобальных имён.
3. `_resolve_type` в semantic.py не меняется: он уже сначала смотрит локальные типы, затем модель;
   шаблонный поиск живёт в модели и виден всем каналам одинаково.
4. Что не меняется: решения `resolve_member`, порядок каналов, текст находки (имя конкретного типа),
   `dynamic_members`, каналы ТЗ/запроса/формы, данные книги.

## 9. Риски

1. **Неверный шаблон** при имени, где литеральный префикс совпадает частично: выбирается самый
   длинный префикс, тесты (а)…(г) держат.
2. **Новые находки** от подмены типа: гейт сравнивает тройки 89/90; любое появление — откат.
3. **Конфигурационные члены** (`ВсеПользователи`) остаются: 110 находок названы, не спрятаны.
4. **Кэш** по конкретным именам не должен расти неограниченно: кэш на время модели, как у типов.
