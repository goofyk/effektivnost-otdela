# Дизайн итерации 15: канал контекста модуля формы в `p1c.check.bsl`

Дата: 2026-10-31. Область: `p1c` (семантика BSL), метрика G плана оптимизации.
Ветка `p1c` — `main`; контур «Эффективность отдела» — `feat/config-effektivnost`.

## 1. Смысл и зачем

Модуль управляемой формы в 1С знает о себе больше, чем видит лексический разбор
текста: у формы есть реквизиты раскладки (`НачалоПериода`, `Список`, `Запись`),
реквизит `Объект` — владелец формы, служебные имена композиции (`Элементы`,
`ЭтаФорма`, `Команды`, `Модифицированность`, `ВладелецФормы`), методы типа формы
(`Закрыть`, `РеквизитФормыВЗначение`, `ОповеститьОВыборе`) и команды формы.
Сегодня `p1c.check.bsl` этого не знает: имя формы-контекста либо
попадает в «нет такой переменной», либо молча проходит как имя неизвестного типа.

Итерация закрывает метрику G — `check.bsl` на `examples/managed_app` даёт
`IDS_STX_VAR_NOTDECLARED` 2 находки в модуле формы, и обе пропадают, когда
реквизиты раскладки становятся известны. Попутно снижаются главные шумы формных
модулей большого корпуса: `VAR_NOTDECLARED` 21 670 и `PROC_NOTDEFINED` 922.

## 2. Цели, нецели, антицели

**Цели.**
- G: `check.bsl` на `examples/managed_app` — с 2 находок до 0 (замер по CLI).
- Реквизиты раскладки формы доступны как имена в её модуле.
- Имена композиции формы (`Элементы`, `ЭтаФорма`, `Команды`, `Модифицированность`,
  `ВладелецФормы`, `ТекущиеДанные`) доступны как имена.
- Реквизит `Объект` формы получает тип из `<Type>` собственного объявления в
  раскладке (не из имени метаданных-владельца и не из папки пути), и
  `Объект.<имя>` разбирается строго. Решение: входит в эту итерацию, порядок
  внутри итерации — «имена → стандартные свойства объектных типов → строгий
  `Объект`» (§6).
- Голые вызовы методов типа формы перестают быть «неопределённой процедурой».
- Каждый закрытый зазор даёт тест в `p1c/tests/check_bsl/`.

**Нецели.**
- Строгая типизация реквизитов (тип из `<Type>` раскладки) — только имена, кроме
  реквизита `Объект` (§5.3).
- Типизация `Элементы.<имя>`, `ЭтаФорма`, элементов макета (`ПолеФормы`,
  `ЭлементФормы`, `КомандаФормы`) — в данных платформы таких типов нет;
  `ЭтаФорма` объявляется именем без типа (замер: 172 `VAR_NOTDECLARED`).
- Свойства формы (`УсловноеОформление`, `КлючТекущегоВарианта`) и свойства
  глобального контекста (`ОбработкаОшибок`, `ПараметрыПриложения`,
  `ПараметрЗапуска`, `КлиентскоеПриложение`, `ОписаниеРасширения`,
  `МодальныйРежим`, `РежимОткрытияОкна`, `ТекущийЭлемент`) — другой канал,
  замеряется отдельно.
- Контекстная разборка `&НаСервере` / `&НаКлиенте` для реквизитов: `Form.xml`
  не кодирует вариант реквизита (в 520 разобранных файлах `<Variant>` нет).
- Проверка «команда формы → действие существует» — это `p1c.check.forms`, не сюда.

**Антицель (почему нельзя «просто типизировать всё»).**
Замерено: строгая типизация реквизитов дала бы 209 новых находок против 92
закрытых обращений; строгий `Объект` без стандартных свойств объектных типов —
334 новых находки (из них 287 — только `Ссылка`). Итерация, которая меняет
10 849 честных `VAR_NOTDECLARED` на шум `PROPERTYNOTFOUND`/`METHODNOTFOUND`,
считается провальной, даже если G закроется.

## 3. Ограничения

- Точки входа семантики фиксированы по сигнатуре:
  `check_module_text(text, ctx, options)` — **без параметра пути**
  (`p1c/check/bsl/semantic.py:877`); путь знает только
  `check_options_for(ctx, path, options)` (`p1c/metadata/module_paths.py:143`),
  куда его передают из четырёх мест сборки (`check/bsl/cli.py:201`,
  `check/bsl/server.py:243`, `cli/runner.py:199`, `lsp/lsp_server.py:257`).
  Значит факт о раскладке может принести только `check_options_for` — через
  `options`.
- LSP передаёт абсолютные URI-пути модулей, CLI — относительные POSIX-пути
  выгрузки. Ключ индекса форм не может быть полным путём.
- Данные платформы (`p1c/src/p1c/data/`) не содержат свойств типов: у
  `Форма` 27 методов и 0 свойств, `ФормаКлиентскогоПриложения` 57/0,
  `ТестируемаяФорма` 15/0; `ПолеФормы`, `ЭлементФормы`, `КомандаФормы`,
  `УправляемаяФорма` в данных отсутствуют.
- Модельные объектные типы собираются только из атрибутов выгрузки
  (`p1c/metadata/loader.py:140-166`): стандартных свойств `Ссылка`,
  `Родитель`, `Владелец`, `ДополнительныеСвойства` в них нет (в корпусе
  `Ссылка` есть лишь у 2 типов из 384).
- Все ключи новых каналов — через `norm()` (`p1c/core/names.py`: регистр + `ё→е`).
- Замеры корпусов — по одному ключу за раз; корпуса только читаются.

## 4. Approaches (как строили, что выбрали)

**A. Только имена контекста формы (реквизиты + композиция), без типов.**
Закрывает 10 849 (`реквизит`) + 10 137 (`композиция`) из 21 670
`VAR_NOTDECLARED` формных модулей и даёт 0 нового шума: имена объявляются без
типа, поэтому `Реквизит.<член>` остаётся в нынешнем «тип базы неизвестен»
состоянии. Минимальный шов: индекс форм + `options["form"]`.
Трейд-офф: `Объект.<имя>` (1 954 обращения) остаётся неразобранным, голые
вызовы методов формы (900) не закрыты.

**B. Строгий вариант: реквизиты с типом из раскладки + `Объект` с типом владельца.**
Даёт разбор `Объект.<имя>` и `реквизит.<член>`, но по замерам приносит 209 + 334
новые находки и требует отдельной предпосылки (стандартные свойства объектных
типов) плюс починки маппинга читателя: тип реквизита `Запись` выгрузка даёт как
`cfg:…RecordManager.<Имя>`, а читатель переводит его в тип **менеджера**
регистра, поэтому `запись.ВладелецФайла` даёт `METHODNOTFOUND`.
Трейд-офф: закрывает 10 849, но меняет характер шума; в текущем состоянии
данных платформы и модели — выгод нет.

**C. Полный контекст формы (выбран).**
Имена без типа (реквизиты + композиция), `Объект` с типом из `<Type>` его
объявления в раскладке (строгий разбор только там, где раскладка объявляет
`Объект`, и только после предпосылки §6),
голые вызовы методов типа формы раньше глобальных функций, декларации команд
формы как данные индекса. Закрывает 10 849 + 10 137 + 900 при нулевом
новом шуме со стороны имён; шум строгого `Объект` вынесен в отдельную
предпосылку (см. §6) и меряется до включения.
Трейд-офф: `Элементы.<имя>` (9 807 обращений) остаётся без разбора членов,
1 863 `METHODNOTFOUND` формных модулей не меняются.

Выбран C: A не трогает главный источник находок в формных модулях после
реквизитов (голые вызовы и `Объект`), B по замерам дороже того, что закрывает.

## 5. Как устроено (решения по частям)

### 5.1 Шов доставки фактов: `ctx.forms` → `options["form"]`

`build_type_model(model, …)` (`p1c/metadata/loader.py:83`) добавляет индекс
форм из того, что уже есть в JSON-модели: `model["objects"][*]["forms"]` и
`model["common_forms"]`. Запись формы даёт всё необходимое
(`p1c/load/reader.py:537-582`): `name`, `object` (имя метаданных-владельца),
`kind` (вид метаданных), `path` (`…/Ext/Form.xml`), `module`
(`…/Ext/Form/Module.bsl`), `attributes`, `items`, `commands`, `events`.
У записей из `model["common_forms"]` поля `object` и `kind` пустые (замер 15:
78 записей — 65 `CommonForms` и 13 форм `SettingsStorages`), поэтому владелец
из них не выводится; `attributes` есть у 73 записей, `commands` у 69, `module`
у всех 78.

Ключ индекса — нормализованный «хвост метаданных» из общей функции
(условно `form_key_of(path)`, `p1c/metadata/module_paths.py`): сегменты пути от
каталога вида метаданных до имени формы, через `/`, свёрнутые `norm()`.
Примеры ключей: `Documents/Х/Forms/Ф`, `SettingsStorages/Х/Forms/Ф`,
`CommonForms/Ф`. Такая функция обязательна, потому что CLI даёт относительный
POSIX-путь, LSP — абсолютный, а запись раскладки известна по относительному
пути выгрузки.

`check_options_for(ctx, path, options)` кладёт в `options["form"]` запись:
`attrs` (имя → `None`), `composition` (имя → `None`), `obj_type` (тип реквизита
`Объект` из раскладки, если модель типов его находит, иначе `None`),
`methods` (имя → сигнатура), `commands` (декларации команд формы). Полная форма
записи — на строителе (§8); смысл один: семантика получает факт о раскладке в
`options`, не меняя сигнатуры.

### 5.2 Канал имён в `resolve_varref`

Новые проверки ставятся там же, где канал владельца итерации 14
(`p1c/check/bsl/semantic.py:608-615`): после `scope.lookup`, до
`collections`. Порядок сознательный: локальная декларация и параметр
процедуры побеждают имя раскладки, а имя раскладки побеждает коллекции,
общие модули и глобальные свойства. Реквизиты и имена композиции объявляются
**с типом `None`** — по замеру §7 (209 промахов против 92 попаданий).

**Имена композиции.** Особых имён формы в таблицах имён семантики нет:
`Элементы`, `ЭтаФорма`, `ВладелецФормы`, `Команды`, `ТекущиеДанные` отсутствуют и
в `global_functions`, и в `global_properties`; `ЭтотОбъект` — есть. Поэтому
`ЭтаФорма` даёт 172 `VAR_NOTDECLARED`, `ВладелецФормы` 60, `Команды` 46,
`ТекущиеДанные` 1 — они разрешаются тем же новым каналом, а не существующей
веткой `resolve_varref`. Их список — фиксированный список имён канала формы
(состав строитель, §9), а не производное от данных платформы: у `Форма` /
`ФормаКлиентскогоПриложения` / `ТестируемаяФорма` поле `properties` пустое, и
`Элементы` / `ЭтаФорма` / `ВладелецФормы` / `Модифицированность` / `ТекущиеДанные` в методах этих трёх типов не встречаются. `Модифицированность` в данных есть, но
как свойство других типов с доступностью без клиентских контекстов
(`p1c/src/p1c/data/platform_arities.py:11496` и далее) — как имя композиции оно
объявляется без типа и без проверки доступности, иначе 51 закрытая находка
превратится в `BSL_CTX_NOT_AVAILABLE`.

### 5.3 `Объект` формы

Тип имени берётся из того, что раскладка уже объявляет: у реквизита `Объект`
в `Ext/Form.xml` есть `<Type>`, и читатель приносит его в
`form["attributes"][*]["type"]`. Замер 14: у 131 формы корпуса реквизит
объявлен, и модель типов находит тип из `<Type>` во всех 131 случаях — 121 раз это
объектный тип модели (`СправочникОбъект.<Имя>`, `ОбработкаОбъект.<Имя>`,
`РегистрСведенийНаборЗаписей.<Имя>`), 9 раз — `Строка`, 1 раз — ссылочный тип.
То есть выводить тип из имени владельца не нужно: он уже записан в раскладке.

Вывод `module_owner(path)` (`p1c/metadata/module_paths.py:111`, тот же приём по
каталогу вида метаданных) для путей модулей форм даёт объектный тип у 127
объектных форм и совпадает с типом из раскладки у 114 из них; у 13 он расходится
(в том же замере 9 реквизитов объявлены как `Строка`, 1 — как ссылка), а у 4
форм из `model["common_forms"]` не работает вовсе: у них `form["object"]` и
`form["kind"]` — пустые строки, и каталога вида метаданных в пути нет. Поэтому
источник — `<Type>` реквизита; имя владельца и папка не используются, и
`options["owner"]` для модуля формы не заводится (он и сейчас ставится только
для `ObjectModule.bsl` / `RecordSetModule.bsl`).

Канал включается только там, где раскладка объявляет реквизит: замер 13 даёт
1 933 обращения `Объект.<имя>` в 127 объектных формах с объявленным реквизитом,
21 обращение в 315 объектных формах без него и 53 обращения в общих формах
(37 из них — в 4 формах, которые `Объект` объявляют: 3 `CommonForms` и одна
форма хранилища вариантов отчётов). Объявлен `Объект` у 131 формы из 520
(127 объектных + 4 в `model["common_forms"]`, куда читатель кладёт и 13 форм
`SettingsStorages`). Если раскладка тип не даёт, имя остаётся без типа — как
сейчас, без нового шума.

### 5.4 Голые вызовы методов типа формы (главный новый канал)

Объединение методов `Форма` (27), `ФормаКлиентскогоПриложения` (57) и
`ТестируемаяФорма` (15) — 81 имя. В `check_call` для вызова
`Имя(…)` (`p1c/check/bsl/semantic.py:699-707`) они проверяются **до**
`ctx.global_functions`, сразу после символов модуля: `scope.lookup` (своя
процедура) остаётся первым. Арность берётся из сигнатуры типа формы,
арность глобальной функции для этих имён не подставляется.
Вариант формы (клиент/сервер) в выгрузке не различим — объединение принято сознательно
(в 520 `Form.xml` `<Variant>` нет).

Политика объединения зафиксирована, причина — в самих таблицах: арности и списки
доступности одного имени трёх типов **объединяются**, а не берутся «из первого типа
по порядку». Замер по данным: у `Закрыть` в `Form` арность 0..1 и доступность
только `thick_client` (`p1c/src/p1c/data/platform_arities.py:5656`), у
`ФормаКлиентскогоПриложения` (`ClientApplicationForm`) — та же арность, но
`thin/web/mobile/thick/mobile_app` (`:2444`); у `ПередЗакрытием` арности разные —
2..2 у `Form` (`:5650`) и 4..4 у `ClientApplicationForm` (`:2433`); у
`ИзменитьРеквизиты` в `ClientApplicationForm` доступность только серверная
(`:2437`). Фактический контекст модуля управляемой формы — `client`, группа
`CONTEXT_GROUPS["client"]` толстый клиент не включает
(`p1c/src/p1c/metadata/model.py:593-596`), а проверка доступности сравнивает
контекст вызова с `availability` сигнатуры (`p1c/check/bsl/semantic.py:845-861`).
Отсюда: «первый тип по порядку» даёт `BSL_CTX_NOT_AVAILABLE` на массовом имени
(`Закрыть` — 344 вызова в базовой линии), а объединение арностей и доступности
закрывает 900 `PROC_NOTDEFINED` без нового шума. Арность глобальной функции (у
имён-подавителей это 0..2**30) в объединение не добавляется: иначе проверка
арности на этих именах становится пустой. Сознательная жертва — строгость
арности одного типа: `ПередЗакрытием` принимает 2..4 (объединение трёх типов),
а не 2..2 и не 4..4. Если объединённый диапазон не покрывает вызов, который
сегодня проходит через `ctx.global_functions`, канал по такому имени не
включается вовсе. Покрытие и цену каждого варианта мерит корпусный прогон до
включения (замер 16): если объединение доступности даёт находки там, где сегодня
чисто, канал по таким именам тоже не включается.

### 5.5 Команды формы

## 6. Предпосылка строгого `Объект`: стандартные свойства объектных типов

Строгий `Объект.<имя>` требует стандартных свойств, которых в модельных типах
нет. Разбор 1 954 обращений дал: 1 620 разрешаются без находок, 334 станут новыми
находками — и это пропуск свойств, а не ошибки в корпусе: `Ссылка` 287,
`Родитель` 14, `БизнесПроцесс` 6, `Выполнена` 5, `Исполнитель` 4, `Владелец` 4,
`Ключ` 3, `Стартован` 3, `Предопределенный` 2, `РольИсполнителя` 2,
`ДополнительныеСвойства`, `ПроверитьЗаполнение`, `УстановитьПометкуУдаления`,
`Завершен` — по 1. В эти 1 954 входят 1 933 обращения из форм с объявленным
реквизитом `Объект` (тип брали из `<Type>` раскладки) и 21 обращение из форм
без него, где замер 4 подставлял тип по пути модуля. Причина:
`loader.build_type_model` регистрирует свойства объектных/ссылочных/записных
типов только из атрибутов выгрузки;
`reader.STANDARD_ATTRIBUTES` (`p1c/load/reader.py:154-166`) добавляет
`Код`/`Наименование`/`Номер`/`Дата`/`ПометкаУдаления`/`Проведён`/`ЭтоГруппа`,
но не перечисленные выше.

Решение (принято владельцем, 2026-10-31): стандартные свойства и строгий
`Объект` **входят в эту итерацию**, порядок «имена → стандартные свойства →
строгий `Объект`» фиксированный. Задача свойств исполняется раньше, и у неё
собственный замер остатка промахов перед включением строгого канала.

Два факта, которые эта задача меняет (и которые её ограничивают):
- `Ссылка` (`p1c/src/p1c/data/platform_global_context.py:814`), `Родитель`
  (`:744`), `Владелец` (`:69`) уже лежат в инвентаре имён и через
  `p1c/src/p1c/metadata/model.py:385-396` доступны как глобальные свойства с
  типом `None`, а `resolve_member` при неизвестном типе базы молча пропускает
  любой член (`p1c/check/bsl/semantic.py:653-654`). Поэтому сама задача свойств
  не закрывает ни одной находки в текущем прогоне: она включает строгий разбор
  тогда, когда тип базы становится известным.
- После добавления свойств ожидаемый остаток промахов — примерно 47 из 334
  (вычитается 287 обращений `Ссылка`); это оценка по распределению замера 4, а
  не замер нового прогона. Отдельно не замерено: глубокие цепочки вида
  `Объект.Ссылка.<член>`, которые станут проверяемыми после типизации. Их стоимость
  меряется прогоном до включения строгого канала, и если они дают шум — строгий
  `Объект` включается только для тех типов, где остаток нулевой.

## 8. Метрики и гейты итерации

- G: `python -m p1c.check.bsl.cli check examples/managed_app --root
  examples/managed_app --format json` → `summary.count` 2 → 0.
- Корпусный гейт (только чтение, corpora_pulsar, один ключ за раз): повтор замера
  по модулям форм; PREDICTIONS пишутся до прогона — `VAR_NOTDECLARED` уменьшается
  примерно на 10 849 + 10 137, `PROC_NOTDEFINED` уменьшается примерно на 900,
  `METHODNOTFOUND`/`CTOR_NOTFOUND`/`PROPERTYNOTFOUND` не растут (кроме
  зафиксированного вклада предпосылки §6), непредсказанные сдвиги разбираются
  отдельно с причиной.
- База гейта — базовая линия §7 (26 102 находки в 502 модулях, 11 кодов),
  повторенная при **тех же** опциях прогона и том же наборе модулей:
  `check_options_for` задаёт `module_kind`/`module_contexts`/`execution_context`
  сам, а коды `BSL_CTX_NOT_AVAILABLE` (8), `BSL_CTX_CLIENT_ONLY` (7) и
  `IDS_STX_PROC_DEFINED` (6) от этих опций зависят, поэтому сравнивать можно
  только прогоны с идентичными опциями. Их базовые значения фиксируются как
  потолок: новый канал обязан оставить их не выше 8 / 7 / 6.
- Тесты: RED-тесты в `p1c/tests/check_bsl/` в стиле
  `tests/check_bsl/test_module_owner.py` (регистрация `TypeDef` поверх
  `builtin_type_model()`, вызов `check_module_text(text, ctx, options=…)`,
  отдельная проверка `check_options_for(ctx, path, {})`) — реквизиты и
  композиция, `Объект` из раскладки, голые вызовы методов формы, команды формы,
  стандартные свойства объектных типов. Затем полный прогон:
  `python scripts/run_tests.py` в `p1c` (сейчас 87/0) и полный прогон контура
  (сейчас 303/303).

## 11. Риски

- Остаток голых вызовов, не покрытый объединением 81 имени (22 имени в корпусе, например
  `Активизировать()` в `DataProcessors/ЗаменаИОбъединениеЭлементов/Forms/ОбъединениеЭлементов/Ext/Form/Module.bsl`
  — не объявлено ни в модуле, ни в раскладке) — остаётся шумом канала.
- Объединение клиентских и серверных методов принимает вызовы, которых в реальном
  варианте формы быть не может (например клиентский `РеквизитФормыВЗначение()` в
  серверной процедуре) — сознательная цена за отсутствие `<Variant>` в выгрузке.
- Коллизия «имя команды == имя процедуры» и «реквизит == локальная переменная»
  решается порядком: `scope.lookup` всегда побеждает канал формы.
- Строгий `Объект` даёт новый шум, если предпосылка §6 исполнена плохо;
  поэтому он включается только после замера остатка промахов.
- Ключ `form_key_of` может совпасть при одинаковых именах форм под разными
  видами метаданных — ключ включает каталог вида, риск остаётся в записи о
  решениях строителя.
