# Итог боевой проверки: конфигурация «Эффективность отдела» против инструментов p1c

Задача была такая: рукописно собрать конфигурацию 1С по реальной бизнес-задаче
(эффективность отдела: факт работ, затраты времени, план загрузки, показатель
«три точки») и максимально покрыть её инструментами `p1c.*`, а то, что инструменты
не видят, задокументировать. Ничего не генерировалось генератором конфигураций —
каждый файл конфигурации написан рукой, и каждый нижеприведённый счётчик взят из
артефакта замера в `reports/`.

Условные обозначения путей: `<work>` — рабочее дерево, `<tmp>` — временный каталог
замеров, `<cfg>` — каталог исходника конфигурации, `<dump>` — выгрузка конфигурации
из ИБ.

---

## 1. Что собрано

Рукописная конфигурация «Эффективность отдела» — 31 файл в `<cfg>`:

| класс файла | сколько |
| --- | --- |
| `object_module` (модули объектов) | 6 |
| `bsl_module` (прочие модули `.bsl`) | 8 |
| `role` + `role_rights` | 2 + 2 |
| `form_descriptor` + `form_data` + `form_module` | 2 + 2 + 2 |
| `report` + `report_template` + `report_template_data` | 1 + 1 + 1 |
| `language`, `subsystem`, `predefined_data` | 1 + 1 + 1 |
| классы объектов (`catalog`, `document`, `enum`, `constant`, `common_module`, `data_processor`, `information_register`, `accumulation_register`) | по 1 |
| **итого файлов** | **31** |

(`gate-14.json` → `layout_source`; артефакты `gate-01.json` … `gate-14.json`.)

Состав объектов: справочник `Сотрудники` (с предопределёнными данными и формой
элемента), документ `ФактРаботы`, перечисление `ГрейдыСпециалистов`, константа
`НормаЧасовВМесяц`, общий модуль `РасчётПоказателей`, обработка `ВыгрузкаЗатратCSV`
(с формой), отчёт `ОтчётЗагрузки` со схемой компоновки данных, регистры сведений
`ПланЗагрузки` и накопления `ЗатратыВремени`, подсистема `ЭффективностьОтдела`,
две роли (`СотрудникОтдела`, `АдминистраторСистемы`), язык `Русский`.

## 2. Конфигурация реально загружается и годна к работе

Это отдельное требование, и оно проверялось не «на глаз», а гейтом:
создание ИБ → загрузка исходника командой платформы → выгрузка → синтаксическая
проверка → независимый контроль метаданных.

Гейт `gate-14.json` (последний прогон, артефакт в `reports/`):

```text
load_code              0        выгрузка: dump_files 32, dump_fresh_files 32
check_code             0        диагностик: "Синтаксических ошибок не обнаружено!"
create_code            null     ib_ready_before true
reason                 ""       step_problems []   diagnostic_findings []
шаги: load 0 / 14.2 с, check 0 / 2.0 с, dump 0 / 2.0 с
```

Четыре последних гейта подряд зелёные и **побайтово идентичны по содержанию**:
`gate-11` … `gate-14` дают одинаковый нормализованный JSON (5451 знак); различается
только время шага `load` — 5.1 с, 2.1 с, 17.3 с и 14.2 с (хронология из замеров
`mtime`: `<tmp>\dump_mtime.py`). Различия шагов объясняются содержимым: гейт-13 шёл
сразу после правки `Template.xml`, гейт-14 — сразу после правки `ManagerModule.bsl`.

Честность контроля: гейт считает метаданные **независимо** от `p1c.load` — по
раскладке файлов и по `ChildObjects` в XML, и сверяет с эталоном
`docs/expected-metadata.json`. Результат `gate-14.json`:

```text
metadata.declared        12 классов (role 2, остальные по 1)
metadata.expected_mismatch   {}
metadata.hard_problems       {}
metadata.layout_mismatch     {}      layout_source == layout_dump (31 файл, 22 класса)
metadata.problems            {}      reason ""
rights.code              0    files 2, object_blocks 17, rights 79
rights_immobility.code   0    dropped [], added []   (17 блоков / 79 прав и в источнике, и в выгрузке)
diff_files: same 21, differ 8, reordered 2, platform_added ["ConfigDumpInfo.xml"],
            only_source [], only_dump []
```

Значит конфигурация загружается без изменений раскладки, без синтаксических ошибок,
а права ролей после загрузки не «осыпаются».

Отдельно закрыт вопрос о правах. Формулировка «права настроены» допускается только
после контроля неподвижности прав — `rights_immobility(источник, выгрузка)` с кодом 0
(`scripts/gate.py:361`). Он выполнен: 17 блоков прав и 79 прав в источнике, те же
17 и 79 в выгрузке, `dropped []`, `added []`, код 0. Канон написаний прав —
`docs/canonical-rights.json`; `p1c` прав не читает вообще, поэтому контроль сделан
своим кодом, а не инструментом.

Живая пригодность тоже подтверждена не только гейтом: выгружена форма внешней
обработки и возвращена в XML (круг `.epf` ↔ XML замкнут), и есть живой отчёт
`ОтчётЗагрузки` со схемой компоновки данных, текст запроса которой проверяется
`p1c.check.sdbl` (см. `docs/evidence/sdbl-controls.md`).

## 3. Ловушки, которые реально сработали

Четыре момента, где «код 0» ничего не означал. Все они закрыты контролем
раскладки, а не кодом возврата; все задокументированы.

**(а) Код 0 при ИБ без конфигурации.** При отказе частичной загрузки платформа всё
равно возвращает 0, и выгрузка получается 3 файла — оболочка ИБ, а не конфигурация.
Отличие видно только по uuid и по числу файлов (`effect-16-loadopts-*.json`,
`effect-16-update-fresh.json`). С тех пор факт загрузки меряется так: `config_uuid`
выгрузки равен uuid конфигурации в исходнике **и** раскладка полная (32 файла).
Ожидание `full-load-keeps-source-uuid` подтверждено (`met: true`).

**(б) `ConfigDumpInfo.xml` — не хеш содержимого.** Одна и та же выгрузка может
получить другой `configVersion`. Поэтому вывод «изменений нет» требует свежей ИБ:
`--fresh-ib` (в артефактах это `ib_fresh_each_step: true`). Лестница `REPEAT`
 (`effect-16-repeat-full.json`) показывает исключение: у неё `ib_fresh_each_step: false`,
и это отдельный, явно задокументированный случай.

**(в) Молчаливый пропуск SKD-шаблонов.** `check.sdbl` изначально обходил только
`*.bsl` (`check/sdbl/cli.py:151`), и текст запроса из `Reports/ОтчётЗагрузки/Templates/
ОсновнаяСхемаКомпоновкиДанных/Ext/Template.xml` вообще не попадал в проверку — при
коде 0 и пустом списке находок. После исправления (`check/sdbl/cli.py:145-154`) тот же
отчёт даёт 1 запрос в `query`-прогоне (`sdbl stats.query.queries 1`). Артефакт
`toolcov_sdbl-query-skd.json`.

**(г) Предопределенные данные.** Модификатор `PredefinedDataUpdate`
(`/SetPredefinedDataUpdate`) по наблюдаемым строкам предопределённых данных неотличим
от его отсутствия (лестница `PREDEFINED`, `effect-16-predefined-full.json`:
6 мутатирующих шагов, все кодом 0, `met` 4 из 7 ожиданий). Отсюда вывод: **наличие**
предопределённых данных в исходнике — факт, который ни один `p1c`-читатель не
подтверждает; его меряет только гейт (`layout_source.predefined_data 1`).

**(д) Дублирующий контроль `.gitignore`.** В репозиторий 3 из 31 файла конфигурации
не попадали, потому что ненастроенный якорь `reports/` проглатывал
`cfg/ЭффективностьОтдела/Reports/**` (на диске 31 файл, в git 28). Исправлено на
`/reports/` и проверено (`git ls-files` и обход диска).

**Отдельный дефект самой конфигурации, найденный корпусом.** В
`InformationRegisters/ПланЗагрузки/Ext/ManagerModule.bsl` стояла директива `&Сервер`
как самостоятельная строка. Проверка шести корпусов (50 309 `.bsl`-файлов) даёт:
`server_standalone_lines` **0**, `server_any` **8**, и все 8 встреч — это имена
параметров запроса `&СерверПодписи` и `&СерверДокументооборота`, а не директива
(`reports/corpora-server-annotation-18.json`). Директива убрана из модуля; гейт-14
подтвердил код 0 и «Синтаксических ошибок не обнаружено!». Что платформа делала с
этой директивой — не измерено (см. раздел 6).

## 4. Покрытие инструментами p1c

Матрица — прогоны самих CLI по нашей конфигурации и по нашей выгрузке
(`probe/tool_coverage.py` → `reports/toolcov_*.json`, сводка
`reports/toolcov_runs.json`). Из матрицы исключены мутатирующие подкоманды
(`cf set`, `cf normalize`). Всего 18 прогонов, из них 15 с JSON-отчётом и 3 без него;
отдельных артефактов 16 = 15 прогонов + `toolcov_runs.json` (плюс
`toolcov_summary.txt`).

Мера одна, но с двумя независимыми признаками, и оба честные:

- `path_hits` — имя класса появилось в пути файла, который инструмент прочитал;
- `name_hits` — имя сущности появилось в отчёте или в консоли как имя сущности.

По 22 классам файлов конфигурации:

| чем подтверждено | классов | классы |
| --- | --- | --- |
| по пути файла | 5 | `bsl_module`, `files`, `form_data`, `form_module`, `object_module` |
| только по имени в отчёте | 10 | `accumulation_register`, `catalog`, `common_module`, `constant`, `data_processor`, `document`, `enum`, `form_descriptor`, `information_register`, `report` |
| ни путём, ни именем | 7 | `language`, `predefined_data`, `report_template`, `report_template_data`, `role`, `role_rights`, `subsystem` |

Гейт независимо даёт `tool_blind_kinds` = 12: `bsl_module`, `files`,
`form_descriptor`, `form_module`, `language`, `object_module`, `predefined_data`,
`report_template`, `report_template_data`, `role`, `role_rights`, `subsystem`.

Разница 12 и 7 объясняется просто и это важно: **5 классов из «слепых для p1c»
инструмент всё-таки читает** — он читает их файлы, но не называет их классом в
отчёте. И наоборот, 10 классов инструментов видят по имени, но не показывают путь.
Полная слепота (ни пути, ни имени) — ровно те 7 классов.

Сверка двух reader-прогонов с гейтом сходится: для `load-model-cfg` и
`load-model-dump` счётчики читателя и гейта равны (`diff_reader_vs_gate {}`).

Тонкость меры, которую надо помнить, перечитывая таблицу: имена `Form`, `Module`,
`Template` — не имена сущностей (`GENERIC_STEMS`); пять классов измеряются только
путём (`PATH_ONLY_KINDS`); хит имени, стоящий вплотную к разделителю пути, — это
отражённый путь, а не имя сущности (`name_hits_path_only_echo`, отдельный признак).

Содержимое отчётов переносит в матрицу только генератор; ключи `context_effective`,
`context_signature`, `schema` из сравнения исключены (`SKIP_REPORT_KEYS`).

## 5. Что показал разбор находок `p1c.check.bsl`

Прогон `bsl-check-cfg`: код 1, 15 находок (`reports/toolcov_bsl-check-cfg.json`).
Разбор каждой (`docs/evidence/tool-coverage.md`, раздел «Следствие для инструментов
p1c»):

| код находки | сколько | вывод |
| --- | --- | --- |
| `IDS_STX_VAR_NOTDECLARED` | 11 | шум канона: неявные реквизиты и `Движения.` в корпусах написаны так же |
| `IDS_STX_METHODNOTFOUND` | 3 | шум канона (методы формы/объекта через каноническое обращение) |
| `IDS_STX_CTOR_NOTFOUND` | 1 | **дефект данных p1c**: конструктор `СообщениеПользователю` отсутствует в модели типов |

Канон выводился из шести корпусов (`probe/corpora_bsl.py` → `corpora-bsl-15.json`,
`corpora-bsl-sizes-21.json`) и сверялся с самомером нашей конфигурации
(`self-canonical-17.json`: 8 `.bsl`-файлов, 28 092 байта). Существующая практика
подтверждена числами: `.Добавить(` 688 873 против `Новый Массив` 109 195;
`?(` 131 355 против `ВЫБОР` 76 270; `Формат(` 121 041 (из них 2 451 с `ДФ=`
внутри). Наш код написан по этому канону — отсюда и то, что 14 из 15 находок
оказались шумом инструмента, а не дефектом конфигурации.

## 6. Чего измерить не удалось (граница меры)

Подтверждённого способа исполнить BSL в ИБ из командной строки нет:

| способ | код | `seconds` | байт `/Out` |
| --- | --- | --- | --- |
| `/RunScript <файл>` | 1 | 2.0–2.1 | 3 |
| `/TESTCLIENT`, `/TESTMANAGER`, `-testFile`, `-testOut`, `-TestOnly`, `/AllowScheduledJobs` | — | 30.3–30.4 (таймаут) | 0 |
| `/EXECUTE` | 1 | 40.3–40.4 | 0 |
| отрицательный контроль `-ZzzNetakoyKomandyNet` | 1 | 40.4–60.3 | 0 (`negative_clean false`) |

(`reports/exec-12-runscript.json`, `exec-12-runscript-console.json`,
`exec-13-test.json`, `exec-13-negative.json`; разбор — `docs/evidence/exec-modes-and-negatives.md`.)

Слово `RunScript` не встречается ни в одном из шести корпусов. Следствия:

- валидность запроса SKD на платформе проверить нельзя — только лексико-синтаксически
  через `p1c.check.sdbl`;
- ENTERPRISE-режим без окон исполнить нельзя: код 1, 107 байт, «Запрещено использование
  окон. Передан ключ DisableStartupDialogs.» (`exec-13-enterprise.json`);
- что платформа делает с директивой `&Сервер` — не измерено;
- COM-мост недоступен: `New-Object -ComObject V83.COMObj` → `REGDB_E_CLASSNOTREG`
  (0x80040154); описание ITS `its.1c.ru/db/v838doc/.../TI000000493»` закрыто доступом,
  `websearch` дал HTTP 403.

Кандидаты headless-проверки модулей измерены: `/CheckConfig`, `/CheckModules`,
`-ExtendedModulesCheck`, `-WarningsAsErrors`, `-noCheck`, `-Module`, `-NBegin`, `-NEnd`,
`-ReportFile`, `-ReportFormat`, `-ReportType`, `-EmptyHandlers`, `-UnreferenceProcedures`,
`-HandlersExistence` — 132 прогона накопительной лестницы на чистой ИБ и на двух
преднамеренно битых ИБ (`reports/check-25-*.json`), и 11 регистровых двойников написаний
(`/CheckModules`, `/CheckConfig`, `-HandlersExistence`, `-ExtendedModulesCheck`,
`/LoadConfigFromFiles`, `-listFile`, `-Format`) двумя лестницами `--casecheck` и `--caseload`
(25 и 12 шагов, `reports/flags-26-*.json`). Разбор — разделы 10–12
`docs/evidence/exec-modes-and-negatives.md`, дословные таблицы — раздел 13 того же файла.
Регистр написания имени команды и имени флага платформа не различает: все 11 двойников совпали со
своими близнецами по коду, байтам `/Out` и строкам объекта.
Здесь остаётся незакрытым: `-IncorrectReferences`, `-ConfigLogIntegrity`,
`-DistributiveModules`, `-UnreferenceProcedures` и `-EmptyHandlers` поодиночке не дают
наблюдаемого различия ни на чистой, ни на битой ИБ; `-ReportFile` не создал файла отчёта
ни разу из 84 запросов; поломка ссылки подсистемы (`Catalog.ТакогоНет`) делает ИБ
незагружаемой (код 1 на шаге `load`) и потому командой проверки не измеряется; регистр
значений модификаторов (`-Format PLAIN` против `-Format Plain`) не измерен.

Два других наблюдения: модификаторы доступа неотличимы от базовой
загрузки (`auth_differs_from_baseline = []`) — это по-прежнему незакрыто; а прочтение прошлых
замеров загрузки исправлено — `-listFile` с файлом-списком даёт код 1 и 337 байт там, где ИБ перед
шагом восстанавливают (отказ частичной загрузки из-за несовпадения идентификаторов конфигурации),
и код 0 и 3 байта на ИБ, куда эта конфигурация уже загружена
(`reports/effect-16-loadopts-{shared,full,fresh,fresh2,fresh3}.json`).
