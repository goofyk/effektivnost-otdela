# Круг `.epf` ↔ файлы: `DumpExternalDataProcessorOrReportToFiles` и `LoadExternalDataProcessorOrReportFromFiles` (замер)

Доказательство того, как именно платформа 1С выгружает и загружает внешнюю обработку через файлы, и
что из этого следует для инструментов p1c. Объект замера — реальная внешняя обработка
`ГПН_КонсольЗаданий.epf` (ключ `epf` в `local.paths.json`), 12262 байта.

Дисциплина лестницы: шесть шагов, каждый меняет ровно одну часть команды (имя команды, первый
аргумент или второй аргумент). В отчёте это зафиксировано ключами `plan` (6 шагов), `plan_diffs`
(5 различий) и `plan_single_command_part` = True. Имена команд взяты из замера имён платформы
`p1c/src/p1c/data/test_cli_flags.json` (426 имён), а не из догадки; вызов платформы повторяет форму
`scripts/ib_loop.py:90-104` с `/DisableStartupDialogs`.

## 1. Шесть шагов

| шаг | команда | аргументы | код | сек | `/Out`, байт | строка `/Out` о времени операции |
|---|---|---|---|---|---|---|
| `dump-dir-epf` | `/DumpExternalDataProcessorOrReportToFiles` | `<work>\epf\dump_outdir`, `<work>\epf\ГПН_КонсольЗаданий.epf` | 0 | 1.7 | 551 | `Выгрузка завершена. Суммарное время выполнения операции: 2970 миллисекунд.` |
| `dump-epf-epf` | `/DumpExternalDataProcessorOrReportToFiles` | `<work>\epf\ГПН_КонсольЗаданий.epf`, `<work>\epf\ГПН_КонсольЗаданий.epf` | 1 | 1.3 | 691 | нет такой строки |
| `dump-epf-dir` | `/DumpExternalDataProcessorOrReportToFiles` | `<work>\epf\ГПН_КонсольЗаданий.epf`, `<work>\epf\dump_outdir` | 1 | 1.1 | 616 | нет такой строки |
| `load-epf-dir` | `/LoadExternalDataProcessorOrReportFromFiles` | `<work>\epf\ГПН_КонсольЗаданий.epf`, `<work>\epf\dump_outdir` | 0 | 1.2 | 495 | `Загрузка завершена. Суммарное время выполнения операции: 470 миллисекунд.` |
| `load-root-dir` | `/LoadExternalDataProcessorOrReportFromFiles` | `<work>\epf\dump_outdir\ГПН_КонсольЗаданий.xml`, `<work>\epf\dump_outdir` | 0 | 1.5 | 508 | `Загрузка завершена. Суммарное время выполнения операции: 3747 миллисекунд.` |
| `load-root-target` | `/LoadExternalDataProcessorOrReportFromFiles` | `<work>\epf\dump_outdir\ГПН_КонсольЗаданий.xml`, `<work>\epf\load_targetdir` | 0 | 1.6 | 511 | `Загрузка завершена. Суммарное время выполнения операции: 3427 миллисекунд.` |

Артефакт: `reports/epf-16-roundtrip.json` (`steps`: `argv`, `code`, `labels`, `out_bytes`,
`out_lines`, `produced`, `produced_dir`, `seconds`, `timed_out`). «сек» в таблице — wall-clock шага
замера (запуск процесса и работа с файлами). Время самой операции платформы — отдельная мера: дословная
строка `/Out` в последней колонке таблицы.

Что следует из шагов по одному:

- `dump-dir-epf` — код 0 и «Выгрузка завершена»: первый аргумент выгрузки — каталог или корневой
  файл выгрузки, второй — целевой бинарный `.epf`.
- `dump-epf-epf` — код 1: вместо каталога подставлен `.epf`, и отказ относится именно к первому
  аргументу.
- `dump-epf-dir` — код 1: тот же вход, но второй аргумент — каталог. Значит второй аргумент выгрузки
  обязан быть файлом, и платформа не подбирает имя целевого `.epf` сама.
- `load-epf-dir` — код 0: те же два аргумента, другая команда. Платформа приняла бинарный `.epf` как
  «корневой файл выгрузки» и выдала другой бинарный `.epf`. Проверка «является ли файл файлом
  обработки или отчёта» смотрит на содержимое, а не на расширение: с текстовым файлом та же позиция
  даёт отказ «Файл 'file://…txt' не является файлом обработки или отчета»
  (`reports/exec-13-test.json`, вариант `extproc-file`).
- `load-root-dir` и `load-root-target` — код 0: загрузка выгруженного корневого XML даёт бинарный
  `.epf` на выходе. Целевой аргумент загрузки может быть каталогом (платформа сама подбирает имя
  файла) или файлом.

## 3. Порядок аргументов читается из снимков каталогов

| позиция аргумента (0 = первый после `/DisableStartupDialogs`) | что стоит |
|---|---|
| 0 | каталог выгрузки |
| 1 | каталог выгрузки |
| 2 | каталог выгрузки |
| 3 | — |
| 4 | корневой файл `.xml` |
| 5 | корневой файл `.xml` |
| вывод | `dump_before_first_root` = **True** |

Артефакт: `reports/epf-16-roundtrip.json::snapshot_positions` — `dump_at` = `[0, 1, 2]`,
`root_at` = `[4, 5]`, `dump_before_first_root` = True. Позиции считаются в argv после
`/DisableStartupDialogs`: в шагах выгрузки на месте первого аргумента стоит каталог (или корневой
файл выгрузки), в шагах загрузки — корневой `.xml`. Подписи аргументов платформа печатает по
позициям, поэтому порядок — наблюдение, а не соглашение.

Отдельно про ранее измеренные двухаргументные формы отказов: `reports/exec-14-dumpproc-args.json`
(код 1, 410 байт `/Out`, подписи аргументов переставлены относительно фактических значений) и
`reports/exec-14-extproc-twoargs.json` (имена путей в выводе платформы искажены — private-use коды
`U+E540`, `U+C540`, `U+8BCC`, `U+19F`). Именно из этих отказов лестница `epf-*` строилась как
лестница, а не как «догадка о форме».

## 4. Дефект первой версии замера (почему запись `epf-15` оставлена)

| что сравниваем | `epf-15-roundtrip.json` | `epf-16-roundtrip.json` |
|---|---|---|
| снимок файлов шага взят из | каталога, который шаг **использует** как вход (ошибочно) | каталога `produced_dir`, который шаг **произвёл** |
| `dump_at` | `None` | `[0, 1, 2]` |
| `root_at` | `None` | `[4, 5]` |
| `roundtrip_closed` | True | True |
| `load-root-dir`: sha1 произведённого `.epf` | `None` | `85bb62b9e61accd0` |
| `load-root-target`: sha1 произведённого `.epf` | `None` | `da32d9fb4e9a09b6` |

В `reports/epf-15-roundtrip.json` снимок файлов шага брался из каталога, который шаг **использовал**
как вход, а не из каталога, который шаг **произвёл**. Следствия, видимые в артефактах:

- ключей `snapshot_positions`, `produced_dir` и sha1 произведённых файлов в `epf-15` нет вовсе
  (`dump_at` и `root_at` = `None`);
- в снимок выгрузки попадал и произведённый `.epf` — `dump_tree` `epf-15` содержит 5 записей (в том
  числе `ГПН_КонсольЗаданий.epf`, 12132 байта) вместо 4 файлов выгрузки;
- `roundtrip_closed` в обеих версиях True, но в `epf-15` это следствие неверного снимка: вывод о
  «круге» был собран из файлов, относящихся к другому шагу.

Запись `epf-15` оставлена в `reports/` как запись версии с дефектом, чтобы вывод «замер был
правильный» не опирался на молчание.

## 5. Чего этот замер не утверждает

- Время самой операции платформы записано в артефакте дословно, в `out_lines` шага: `Выгрузка завершена.
  Суммарное время выполнения операции: 2970 миллисекунд.` (`dump-dir-epf`), `Загрузка завершена. Суммарное
  время выполнения операции: 470 миллисекунд.` (`load-epf-dir`), `…: 3747 миллисекунд.` (`load-root-dir`),
  `…: 3427 миллисекунд.` (`load-root-target`); у отказных `dump-epf-epf` и `dump-epf-dir` такой строки нет
  (последняя колонка таблицы §1). Отдельного числового ключа для него в `epf-16-roundtrip.json` нет.
  Поэтому сравнение «загрузка из бинарного `.epf`» (470 мс) против «загрузки из выгруженного XML» (3747 и
  3427 мс) держится ровно на этих четырёх строках; wall-clock шагов (1.2 с против 1.5 и 1.6 с) в сравнение
  не берётся, потому что в него входит запуск процесса. Все три шага загрузки производят по одному файлу
  `ГПН_КонсольЗаданий.epf` (12132 / 12035 / 12035 байт), так что результат шагов сопоставим; но замер не
  разделяет чтение бинарного контейнера и сборку объекта из `XML`-файлов — 470 против 3747 это полное время
  операции, а не стоимость чтения.
- Ни один из шагов не трогает базу конфигурации: полигон — отдельный каталог
  `<work>\epf` (`dump_outdir`, `load_targetdir`), а не гейт-ИБ.
- `/Out` шагов: 551 / 691 / 616 / 495 / 508 / 511 байт; это полный объём файла вывода (`out_bytes`,
  `out_lines`), а не первые строки.

## Следствие для инструментов p1c

1. `p1c` строит пару «выгрузка ↔ загрузка» как симметричную, но аргументы несопоставимы: у выгрузки
   второй аргумент — файл, у загрузки второй аргумент — каталог или файл. Любая попытка «просто
   поменять команду местами» даёт код 1 (шаги `dump-epf-dir`, `dump-epf-epf`).
2. Круг не сохраняет содержимое: 12262 → 12132 → 12035 байта, и два прогона загрузки одной и той же
   выгрузки дают разное содержимое при одинаковой длине. Инструмент, который проверяет «выгрузили и
   загрузили одно и то же» по байтам, обязан сравнивать дерево файлов выгрузки (sha1 каждого файла),
   а не бинарный `.epf`.
3. Печатный вывод платформы по аргументам искажен (private-use коды) и подписи аргументов
   переставлены — разбор подписей из `/Out` в `p1c` (`scripts/platform_name_pairs.py:1519-1525`)
   нельзя считать надёжным источником порядка аргументов.

## Что с этим делать (часть плана оптимизации p1c)

1. Зафиксировать в p1c форму команды выгрузки и загрузки как разные сигнатуры (каталог/корневой файл
   + файл-цель против корневой файл + каталог или файл) и выдавать отдельную находку при подстановке
   каталога вместо файла.
2. Контролировать факт операции по произведённым файлам (`produced_dir` + sha1 каждого файла), а не
   по коду возврата 0: `load-epf-dir` даёт код 0 и файл, которого в исходном наборе нет.
3. Сравнивать круг по дереву файлов выгрузки (пути + байты + sha1), с явным выводом «бинарный
   контейнер не воспроизводится», и не объявлять `roundtrip_closed` без снимка именно произведённого
   каталога (дефект `epf-15`).
4. Выделять время операции платформы в отдельное поле отчёта: платформа сама печатает его в `/Out`
   (`Суммарное время выполнения операции: N миллисекунд` — в нашем замере 2970 / 470 / 3747 / 3427),
   а `exec_probe`-подобные замерщики сохраняют только wall-clock шага. Без отдельного поля
   «быстрее/медленнее» приходится выводить из полного времени операции, в котором не разделены чтение
   контейнера и сборка объекта из `XML`.
