# Контроли `p1c` для запросов: `check`, `query`, `fields` (замер)

Доказательство того, что делает и чего не делает CLI `p1c-check-sdbl` на нашей конфигурации: какие
прогоны дают код 0 без проверки полей, какие написания запросов разбираются с ошибкой, где отчёт
не записывается вообще, и где вывод не меняется от исправления запроса.

Обозначения в таблицах (полные пути записаны в `local.paths.json`, в tables они свёрнуты):
`<repo>` — корень этого репозитория, `<work>` — рабочее поле 1С-замеров (временный каталог
замеров), `<tmp>` — временный каталог прогонов, `<запрос>` — имя, которое `p1c` присваивает источнику
запроса, поданному строкой в `query`.

## Форма вызова и как читается вывод

Вызов (рабочий каталог — корень репозитория, `PYTHONPATH` указывает на `p1c/src` этого рабочего
поля):

```text
python -m p1c.check.sdbl.cli check <путь к cfg или .bsl> [--root <корень выгрузки>] [--no-model] [--format json] [--out <файл>]
python -m p1c.check.sdbl.cli query "<текст запроса>" [--root <корень выгрузки>] [--format json] [--out <файл>]
python -m p1c.check.sdbl.cli fields <имя объекта> [--root <корень выгрузки>] [--format json] [--out <файл>]
```

Код возврата живёт только в сводных файлах прогонов (`reports/sweep_summary.txt`,
`reports/sweep2_summary.txt`, `reports/sweep3_summary.txt`, `reports/sweep4_summary.txt`,
`reports/skd_q_summary.txt`, `reports/skd2_summary.txt`); JSON-отчёт `p1c.result/v1` ключа с кодом не
содержит. Сводка `skd2_summary.txt` начинается заголовочной строкой — парсер, который принимает её
за блок прогона, путается.

Хвосты команд в таблицах помечены `†`, если сводка прогона не записала их дословно: тогда хвост
восстановлен по записанным в артефактах величинам — `query source line:` из сводки `sweep4_*`,
текстам из `reports/skd_q_texts.json`/`reports/skd2_texts.json` и ключу
`context_effective.context.config.root` из самого JSON-отчёта. Такой хвост описывает прогон, а не
дословную строку командной строки.

Дословный отказ (stderr, четыре прогона с кодом 2):

```text
Нужен корень выгрузки или config.root: поля берутся из модели
```

При коде 2 файл, указанный в `--out`, **не создаётся**: `reports/sweep_fields-bare-name.json`,
`reports/sweep_fields-platform-kind-dump.json`, `reports/sweep_fields-platform-kind-src.json` и
`reports/sweep2_fields-no-root.json` в артефактах отсутствуют. Отчёт `p1c.result/v1` при отказе не
пишется, и «почему не получилось» остаётся только в stderr.

Что работает: внутреннее имя вида (`catalog.Сотрудники`) — код 0 и отчёт с ключами
`common_attributes`, `fields`, `kind`, `object`, `schema`, `sections`, `standard_fields`
(`reports/sweep_fields-internal-kind.json`; в этом отчёте **нет ключа `schema_available`** — он есть
во всех отчётах команд `check` и `query`, и именно поэтому в таблице выше этот прогон помечен
«нет ключа в отчёте»). Платформенное имя вида (`Справочник.Сотрудники`) и голое имя справочника
(`Сотрудники`) — код 2. Имя объекта нужно подавать в написании модели p1c, а не в написании
платформы, и это не документировано в самом выводе отказа.

## Следствие для инструментов p1c

1. `check` без схемы (`--no-model` или без `--root`) и проверка каталога без файлов запросов дают
   код 0: «проверка прошла» неотличимо от «проверку не выполняли».
2. `context_signature` считается по написанию аргументов пути, а не по содержанию проверки.
3. `fields` принимает только внутренние имена видов, при отказе пишет сообщение в stderr и не пишет
   отчёт; ключ `schema_available` в отчёте `fields` отсутствует.
4. Суффиксы виртуальных таблиц `Итоги`, `Движения`, `СГРУППИРОВАТЬ` грамматикой не распознаются:
   одно написание даёт синтаксическую ошибку, другое — тихий пропуск.
5. Временные таблицы: отсутствие таблицы — warning при коде 0, поля временных таблиц не проверяются.

## Что с этим делать (часть плана оптимизации p1c)

1. Различать в коде возврата «проверка не выполнялась» и «проверок нет»: при `schema_available` =
   False и `stats.files == 0` — отдельный код (или предупреждение в отчёте), а не 0.
2. Нормализовать путь `--root` (абсолютный или относительный путь, прямой и обратный слэш) до
   вычисления `context_signature`, чтобы подпись зависела от проверяемого содержания.
3. Принять в `fields` платформенные имена видов (`Справочник.<имя>`) и голое имя объекта — через
   перевод имени вида по `p1c/src/p1c/data/query_canonical_map.py` и `QUERY_FIELDS`, и писать
   отчёт `p1c.result/v1` при любом коде отказа (сейчас `cli.py:284-291` выходит до записи отчёта).
4. Добавить суффиксы `Итоги`, `Движения`, `СГРУППИРОВАТЬ` в `DOT_MODE`
   (`p1c/grammars/SDBLLexer.g4:241-252`) и `virtualTable` (`p1c/grammars/SDBLParser.g4:340-353`)
   и подставлять их поля (ресурсы и измерения) в схему проверки.
5. Повышать `IDS_SDBLERR_TEMPTABLENOTFOUND` до уровня, влияющего на код возврата, и проверять поля
   обращений к временным таблицам по описанию `ПОМЕСТИТЬ`.
6. Читать `<query>` из SKD-шаблонов, чтобы `check` сам находил запрос отчёта: в этих замерах текст
   приходилось подавать в `query` вручную, иначе ни один запрос отчёта не проверяется.
7. Исправить `_diagnose` (`p1c/src/p1c/sdbl/sdbl.py:340`) — при несогласованных позициях ошибка
   диагностики превращается в отказ команды вместо находки.
