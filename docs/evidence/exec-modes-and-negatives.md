# Исполнительные формы командной строки 1С: что удалось измерить, а что нет

Измерения делались скриптом `scripts/exec_probe.py` (лестницы `SWEEP`, `CONTROLS`, `NEGATIVE_LADDER`,
`AUTH_LADDER`, `TEST_LADDER`, `MODE_LADDER`, лестницы группы проверки `CHECK_LADDER` и
`CHECKCMD_LADDER`, лестницы регистровых двойников имён `CASECHECK_LADDER` и `CASELOAD_LADDER` и
одиночные контроли) на временной ИБ, никогда на ИБ
гейта и никогда одновременно с живой ИБ пользователя. Каждый шаг лестницы меняет ровно одну часть
командной строки, поэтому различие исходов приписывается именно этой части. Код возврата платформы
в этих прогоны отвечает только за дисциплину лестницы: исход живёт в `bytes` (размер `/Out`),
в дословном списке строк `/Out` и в признаке `timed_out`.

Пояснение о путях: в цитируемых командах и строках `/Out` машинный префикс свёрнут до `<tmp>` (временный каталог замеров) и до `<repo>` (рабочее дерево). Полные строки замера лежат в артефактах `reports/exec-*.json`; байты, коды и секунды в таблицах — дословные значения артефакта. Искажённые глифы, которые платформа вывела вместо имён путей, записаны escape-последовательностями (`\uc540` и т. п.), потому что один из них невидим; речь про U+C540, U+8BCC, U+19F и U+E540, U+C079, U+1B9 (подробнее — раздел 8).

Запись «маркер BSL» означает: в скрипте, который мы просили платформу выполнить, была строка
`P1C-EXEC-MARKER`, и мы искали её в журнале `/Out` и в консоли процесса. Ни в одном прогоне маркер
не появился. «3 байта» в колонке байт — это пустой журнал из одного BOM: платформа создала файл, но
не написала в него ни строчки.

## 1. `/RunScript <файл>`: 12 написаний вызова — один и тот же исход

Измерено 12 вызовов `/RunScript <файл>`: 5 в `reports/exec-12-programs.json` (рабочий скрипт
с маркером в cp1251, битый скрипт, отсутствующий файл, скрипт в utf-8, скрипт только из ASCII)
и 7 в `reports/exec-12-sweep.json` (тот же скрипт в utf-8, utf-8 с BOM и cp1251, плюс написания
с `/authoff`, `-User=… -Pwd=…`, `-CurrentUser` и с внешней ИБ). Все 12: код 1,
2.0-2.1 с, `/Out` 3 байта (пустой), маркера нет. Контроль `RunScript` вообще без аргумента
(`runscript-noarg`) даёт ровно те же 1 / 2.0 с / 3 байта.

Отдельно `runscript_matches_load_noarg = false` и `runscript_matches_load_ok = false`: журнал
загружающей команды при ошибке содержит строку («Файл не обнаружен ''»), журнал `/RunScript` —
ни строки.

**Следствие для инструментов p1c.** Ни один способ исполнить BSL из командной строки не даёт
ни результата скрипта, ни объяснения отказа. Поэтому `p1c` не может ни запустить наш код в ИБ, ни
проверить запросы, которые исполняются только в ИБ (запрос схемы компоновки данных, запросы
обработок). Пустой журнал при коде 1 — это не «ошибки нет»: отсутствие строк должно считаться
отсутствием доказательства, а не успехом.

**Что с этим делать (часть плана оптимизации p1c).** Не строить в `p1c` инструмент «проверить
запрос запуском в ИБ». Проверку запросов делать статически (sdbl), а в отчётах прямо писать, что
исполнение BSL в командной строке данной платформы (8.3.27.1606) не подтверждено ни одной формой.

## 2. `/EXECUTE`: процесс не заканчивается

`/EXECUTE <файл>` и `/EXECUTE <файл> /authoff`: код 1, 40.3-40.4 с (это наш таймаут, не ответ
платформы), `/Out` 0 байт. Для сравнения: `/RunScript` с тем же скриптом заканчивается за 2.0 с.

**Следствие для инструментов p1c.** Форма, которая висит дольше таймаута, не может быть частью
автоматической лестницы: она не различает «команда не существует», «команда требует GUI» и
«команда ждёт пользователя».

## 3. Модификаторы доступа неотличимы от базовой загрузки

Лестница `AUTH_LADDER`: базовая `load-ok` и четыре модификатора (`/authoff`, `-AllUsers`,
`-CurrentUser`, `-User=… -Pwd=…`) — все код 0, 2.0-3.0 с, `/Out` 3 байта. Ключи отчёта:
`auth_same_as_baseline` = все пять вариантов, `auth_differs_from_baseline` = [], `auth_timed_out` = [].

**Следствие для инструментов p1c.** На файловой загрузке конфигурации модификаторы доступа
наблюдаемо не влияют ни на что: их нельзя ни «проверить», ни «исключить как лишние». В документации
`p1c` их надо описывать как параметры подключения к серверной ИБ, а не как параметры
`/LoadConfigFromFiles`.

## 4. Контроли загружающей команды: здесь платформа говорит

`load-ok`: 0 / 3.0 с / 3 байта. `load-noarg`: 1 / 40 байта / строка `Файл не обнаружен ''`.
`load-baddir`: 1 / 117 байт / строка `Файл не обнаружен '<несуществующий каталог>'`.
`controls_distinct = true`: три разных исхода на трёх шагах, меняющих одну часть команды.

**Следствие для инструментов p1c.** Дешёвый способ отличить «загрузка не выполнена» от «загрузка
выполнилась пустотой» — читать строки `/Out`, а не только код. Именно так устроен `empty_dump_detected`
в `scripts/gate.py`: код 0 без выгруженных файлов считается отказом.

## 5. Отрицательные контроли имён флагов: `-<несуществующее>` подвешивает процесс

`/ZzzNetakoyKomandyNet`: код 1, 2.0 с, 70 байт, строка `Пользователь ИБ не идентифицирован`.
`-ZzzNetakoyKomandyNet`: код 1, 40.4-60.3 с (наш таймаут), `/Out` 0 байт. Отсюда
`negative_clean = false`: «несуществующее имя с дефисом» неотлично от зависания, и по нему нельзя
проверять, что платформа знает данное имя.

**Следствие для инструментов p1c.** Отрицательный контроль пригоден только для имён с косой
чертой. Положительный контроль устроен иначе: имена из замера, которые лестницы реально
передают, дают код 0 (`-files`, `-RebuildConfigurationExtensions`,
`/CheckCanApplyConfigurationExtensions` в `reports/effect-16-*-full.json`), а вывод о
несуществующем имени делается по членству в замере
`p1c/src/p1c/data/test_cli_flags.json`, а не по коду возврата.

## 6. Тестовые формы запуска: восемь вариантов, ноль строк журнала

`/TESTCLIENT <файл>`, `/TESTCLIENT`, `/TESTMANAGER <файл>`, `/TESTMANAGER`, `-testFile <файл>`,
`-testOut <файл>`, `-TestOnly`, `/AllowExecuteScheduledJobs` — все: код 1, 30.3-30.4 с (таймаут),
`/Out` 0 байт. Ключи отчёта: `test_timed_out` перечисляет все восемь, `test_silent_variants` —
ещё и базовый `/RunScript`, `test_output_variants` = `enterprise-runscript`, `extproc-file`,
`extproc-noarg` (то есть журнал написан только там, где ругается сама платформа).

**Следствие для инструментов p1c.** В `p1c` нет и не может быть «прогона тестов 1С из
командной строки». Тесты платформы для нас — закрытая зона; проверять поведение кода можно только
статически или через внешние обработки (раздел 8).

## 7. `ENTERPRISE` без окон невозможна

`enterprise-plain` (программа `ENTERPRISE`, `/DisableStartupDialogs`, `/authoff`) и
`enterprise-runscript`: код 1, 1.0-2.0 с, `/Out` 107 байт, дословно
`Запрещено использование окон. Передан ключ DisableStartupDialogs.`

**Следствие для инструментов p1c.** Любая попытка читать данные через интерфейс
`1cv8c`/`ENTERPRISE` в автоматике обречена; это же объясняет, почему `p1c` не может читать то, что
видно только в форме (описание формы, права в интерфейсе).

## 8. Внешние обработки: порядок аргументов и mojibake

`/LoadExternalDataProcessorOrReportFromFiles <файл, не являющийся обработкой>`: код 1, 475 байт,
пять строк, среди них `Целевой каталог или файл: \uc540\u8bcc\u019f` (U+C540, U+8BCC, U+19F — искажённое имя
пути) и `Файл 'file://…' не является файлом обработки или отчета.`
Без аргумента: код 1, 200 байт, пять строк (последняя пустая); оба пути платформа вывела искажёнными
символами: `\ue540\uc079\u01b9` — оба пути искажены одинаково, первый глиф лежит в private-use зоне Unicode (U+E540), то есть платформа
печатает отсутствующий аргумент, а не наш путь.
Искажённые глифы в цитатах `/Out` здесь записаны escape-последовательностями (`\uc540\u8bcc\u019f`, `\ue540\uc079\u01b9`), потому что один из них невидим, а другие печатаются иероглифами: речь про U+C540, U+8BCC, U+19F (прогон `extproc-file`) и U+E540, U+C079, U+1B9 (прогон `extproc-noarg`). В артефакте `reports/exec-13-test.json` эти же символы стоят литерами.
Двухаргументный контроль `/DumpExternalDataProcessorOrReportToFiles <файл> <каталог>` (код 1,
410 байт) показывает, что платформа подписывает аргументы наперекос: в строке
`Входной бинарный файл:` оказывается второй аргумент, а в
`Каталог или корневой файл выгрузки:` — первый. Тот же порядок строк подтверждает
`Формат: Иерархический` без всякого `-Format` в команде.

**Следствие для инструментов p1c.** Круг «`.epf` → XML → `.epf`» (docs/evidence/epf-roundtrip.md)
замыкается только когда аргументы стоят в том порядке, который платформа реально читает; подпись
аргументов в выводе платформы нельзя использовать как доказательство того, что мы передали их
правильно. Пустые имена в журнале — не искажение нашего вызова: платформа печатает
отсутствующий аргумент искажёнными символами, и парсить такой журнал нельзя.

## 9. Режим программы (`DESIGNER` против `CONFIG`) наблюдаемо не влияет

Лестница `MODE_LADDER` меняет один токен в позиции 0: `DESIGNER` → `CONFIG`
(`ladder_token_positions`), остальные токены идентичны. Оба шага: код 0, 2.0 с, `/Out` 3 байта,
`ladder_single_command_token = true`.

**Следствие для инструментов p1c.** Выбор режима — не то, что можно проверить по выводу журнала `/Out`;
его надо фиксировать в самих вызовах (загрузка конфигурации работает и в `CONFIG`), а различие
режимов доказывать формой вызова, а не исходом.

## 10. Группа проверки: `/CheckModules` и `/CheckConfig` приняты, одно имя меняет вердикт

**Что мерили.** Две зеркальные лестницы по 22 шага: `CHECK_LADDER` (команда
`/CheckModules`) и `CHECKCMD_LADDER` (команда `/CheckConfig`) — те же 22 суффикса, различие
только в токене команды (`check_mirror_same_tail = true`,
`check_mirror_differs_by_command_only = true`). Имена взяты только из замера
`p1c/src/p1c/data/test_cli_flags.json`: 17 имён группы проверки — 2 команды, 7 имён,
цитированных в шести корпусах, и 8 имён, в корпусах не цитированных. Значения либо с
читаемым источником (`mxl`, `txt`, `Brief`, `ByObjectNames`, `ByObjectIDs`,
`-Module=РасчётПоказателей`), либо выдуманные явно (`ZzzNetakogoZnacheniyaNet`). Шаг 1 —

меняют: обещать что-то от них в выводе `p1c` нельзя.

## 11. Группа проверки на преднамеренно битой ИБ: ожидания (до прогонов) и результат

### Ожидания, записанные до прогонов

Рецепт битой ИБ (чтобы диагноз нельзя было объяснить чем-то другим): копия
`cfg\ЭффективностьОтдела` → `python scripts/mutate.py <вид_поломки> <копия>` (одна поломка,
исходник нетронутый) → `python scripts/ib_loop.py --ib
<tmp>\p1c_effektivnost\broken_ib_<вид> --cfg <копия> --steps create,load` → те же две
лестницы на этой ИБ, по одному прогону за раз, без `--allow-mutating`. Виды поломки и что
именно они ломают — из `scripts/mutate.py`: `unknown_function_call` (в модуль объекта
`Documents/ФактРаботы/Ext/ObjectModule.bsl` добавлен вызов
`РасчётПоказателей.ПроверитьЧасыДокумента()`), `form_missing_handler` (из модуля формы
`Catalogs/Сотрудники/Forms/ФормаЭлемента` удалена процедура `ПриСозданииНаСервере`,
объявленная в `<Event name="OnCreateAtServer">`), `subsystem_bad_content` (в Content
подсистемы ссылка `Catalog.Сотрудники` заменена на `Catalog.ТакогоНет`).

1. **Базовая команда на битой ИБ молчит.** Ожидание: `/CheckModules` → код 0 и 73 байта
   `Синтаксических ошибок не обнаружено!`; `/CheckConfig` с каноническим `CHECK_KEYS` → код 0

## 12. Регистронезависимость написаний имён: 11 двойников — 11 совпадений с близнецами

**Что такое шаг-двойник.** Двойник — копия уже измеренного шага, у которой ровно один токен
команды перезаписан по регистру: `/CheckModules` → `/checkmodules` и `/CHECKMODULES`,
`/CheckConfig` → `/checkconfig` и `/CHECKCONFIG`, `/LoadConfigFromFiles` →
`/loadconfigfromfiles`, `-HandlersExistence` → `-handlersexistence` и `-HANDLERSEXISTENCE`,
`-ExtendedModulesCheck` → `-extendedmodulescheck` и `-EXTENDEDMODULESCHECK`, `-listFile` →
`-listfile`, `-Format` → `-format`. Всё остальное в строке запуска остаётся близнецовым: тот же
режим, те же модификаторы доступа в том же порядке, та же ИБ, та же программа и кодирование,
тот же канал `/Out`. Личное имя файла `/Out` содержит имя варианта (так устроен контур), поэтому
сравнивается содержимое файла, а не его имя. Отличие двойника от близнеца считается по фактическому
argv (`case_spelling_pairs[*].changed_tokens`), а не по нашей формулировке: у всех 11 шагов
изменён ровно один токен и изменение только регистровое (`case_spelling_register_only = true`,
`ladder_single_command_token = true`, `ladder_multi_token_steps = []`).

**Дисциплина лестницы.** Двойники прогоняются внутри обычной лестницы, а не отдельным списком, и
два двойника одного близнеца не имеют права стоять соседними шагами: между ними обязан встать
этот же близнец — он работает «сбросом» состояния. Это проверяет `case_twin_adjacency`, её результат
в артефактах — `case_twin_adjacency_problems = []`. Сравнение «двойник → близнец» происходит внутри
одного прогона, по классу исхода (`outcome_key`: код, зависание, пустой/непустой `/Out`) плюс байты
`/Out` и число строк `ВидОбъекта.ИмяОбъекта`.

**Откуда взяты написания.** Имя близнеца — измеренное (замер 426 имён
`p1c/src/p1c/data/test_cli_flags.json`, поле `files[].names`); написание двойника — тот же корень
со сменой регистра, и самого написания двойника в таблице 426 имён нет (внешняя сверка:
`case_in_measured = false` у всех 11, `lower()`-совпадение ровно одно — с именем близнеца).
Для двух имён загрузки источник у строчного написания есть и в корпусах: синопсис комментария
пишет `[-files][-listfile][-format]` (`docs/evidence/cli-canonical-usage.md`, строка 47), `-listfile`
— 10 вхождений в шести корпусах (`reports/corpora-cli-usage-16.json`), тогда как `-listFile` — 3
вхождения в БСП. Написания группы проверки (`/checkmodules`, `/CHECKCONFIG`, `-HANDLERSEXISTENCE`)
ни в одном корпусе и ни в одной таблице имён не встречаются — эти написания придуманы нами специально:
вопрос был не «встречается ли такое написание в корпусах», а «различает ли платформа регистр».

**Почему у двойников нет предсказаний.** Предсказание обязано иметь читаемый источник, а источником
для двойника мог бы быть только замер его близнеца — то есть предсказание по будущему замеру, круг.
Отдельный род предсказаний «измеренный близнец предсказывает двойника» для этих шагов отклонён, и
причина у него не одна:
- близнецы группы проверки на битой ИБ уже дали три опровергнутых предсказания (раздел 11), то есть
  их исход нельзя переносить на другой шаг как надёжный;
- у близнецов формы загрузки исход зависит от состояния ИБ, а не от написания: `-listFile
  <файл-список>` и `-Format` дают код 1 и 337 байт в четырёх артефактах LOADOPTS-лестницы, где ИБ
  перед шагом восстанавливают (`reports/effect-16-loadopts-{fresh,fresh2,fresh3,full}.json`; дословно
  `Файл - Configuration.xml: ошибка частичной загрузки - идентификатор … загружаемой конфигурации
  отличается от идентификатора … сохраненной конфигурации` — отказ частичной загрузки из-за
  несовпадения идентификаторов, §5 и §10 `docs/evidence/modifier-effects.md`), и код 0 и 3 байта там,
  где эта конфигурация в ИБ уже загружена (`reports/effect-16-loadopts-shared.json`) — предсказание

- `load-ok` стабилен (код 0 и 3 байта во всех 32 его вхождениях в артефакты `reports/`), но перенести

— отказ частичной загрузки из-за несовпадения идентификаторов: перед этими шагами ИБ восстанавливают,
и её сохранённый идентификатор не совпадает с идентификатором загружаемой конфигурации (§5 и §10
`docs/evidence/modifier-effects.md`). Полная загрузка тем же прогоном при этом проходит: `load-ok`
даёт код 0 и 3 байта. На ИБ, куда та же конфигурация уже загружена
(`reports/effect-16-loadopts-shared.json`, `reports/flags-26-caseload.json`), те же шаги дают код 0
и 3 байта. От состояния ИБ не зависит только исход `load-listfile-onefile`: 1 и 90 байт во всех пяти
LOADOPTS-артефактах и в caseload-прогоне.

Три оговорки, без которых вывод читается шире, чем он есть.

1. **Различимость измерялась только по вердикту, не по следу программы.** Для этих двух лестниц
   BSL-программа не пишется и не исполняется (`needs_script` для шагов группы проверки и загрузки
   ложен): `script_bytes 0`, `marker_exists false` у всех 37 шагов, `executed_variants = []`.
   Совпадение двойника и близнеца доказано кодом возврата, байтами `/Out` и строками объекта.
2. **Закрыт только регистр написания имени, а не регистр значения.** `-Format PLAIN` против
   `-Format Plain`, регистр значений `-ReportFormat`/`-ReportType` — не измерены.
3. **11 двойников — это 11 написаний из 426.** Остальные имена таблицы регистровых двойников не
   имели; регистр BSL-аннотаций (`&НаСервереБезКонтекста` против `&НаСервереБезконтекста`) к этому
   замеру отношения не имеет — он про argv командной строки.

**Следствие для `p1c`.** Платформа 8.3.27.1606 не различает регистр написания имени команды и имени
флага в argv: ни в группе проверки (4 имени, 8 написаний), ни в форме загрузки (3 имени, 3
строчных написания) наблюдаемой разницы нет. Значит `p1c` не может пользоваться разницей написаний
как признаком чего-либо — и не должен хранить два написания как два разных флага (пункт F6 плана
решается в пользу «зафиксировать одно написание»: измеренное `-listFile`, `/CheckConfig`,
`/CheckModules`). Проверять регистронезависимость тестом `p1c` нечем: единственный наблюдаемый
канал — код и `/Out`, а в них разницы нет.
